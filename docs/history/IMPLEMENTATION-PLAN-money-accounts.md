# طرح پیاده‌سازی — «تعریف حساب بانکی / صندوق / کیف‌پول با موجودی اولیه + اتصال خودکار»

> وضعیت: **فقط طرح — هیچ کدی نوشته و اجرا نشده است.**
> قید قطعی: **هیچ تغییری در هسته حسابداری، دفترکل، FIFO، اسکیمای دیتابیس، فایل‌های production و سرویس‌های موجود انجام نمی‌شود.**
> این قابلیت یک لایه «بالای» هسته است و فقط از مسیرهای عمومی موجود (`postEntry`، `accounts`، `wallets`) استفاده می‌کند — دقیقاً مانند `completeSetup` در `src/features/setup/service.ts`.

## ۱) هدف و رفتار نهایی (User Story)

- کاربر (هر تعداد حساب که دارد) یک «حساب بانکی / صندوق / کیف‌پول» تعریف می‌کند.
- در همان فرم: نام کامل + نوع + ارز/دارایی + **موجودی اولیه** وارد می‌کند.
- بلافاصله و بدون هیچ تغییر در ماژول تراکنش یا دفتر حساب‌ها:
  1. در **«پرداخت از حساب»** (فهرست primary در فرم تراکنش) ظاهر می‌شود.
  2. در **«نمودار کامل حساب‌ها / دفتر حساب‌ها»** با موجودی‌اش نمایش داده می‌شود.
  3. در **صفحه‌ی «حساب‌ها»** با موجودی‌اش نمایش داده می‌شود.
- هیچ کاربر دیگری آن را نمی‌بیند و به اطلاعاتش دسترسی ندارد.

## ۲) اصول و قیدهای طراحی (بایدها و نبایدها)

### نبایدها (خط قرمز)
1. **عدم تغییر هسته:** `postEntry`، `reverseEntry`، `recordBuy/Sell/Transfer/Income/Expense`، `consumeFifo`، `assertBalanced` دست‌نخورده می‌مانند.
2. **عدم تغییر اسکیما:** هیچ ستون/جدول/مایگریشن جدیدی اضافه نمی‌شود. از `wallets`، `accounts`، `journalEntries`، `postings`، `lots` موجود استفاده می‌شود.
3. **عدم ثبت موجودی خارج از دفترکل:** موجودی اولیه با یک سند `opening` از مسیر `postEntry` ثبت می‌شود، نه درج مستقیم در `postings` و نه هیچ ستون «balance».
4. **عدم ورود نام بانک به جدول مشترک:** نام حساب/بانک فقط در `wallets.name` و `accounts.name` (که `userId` دارند) ذخیره می‌شود. جدول `institutions` (که `userId` ندارد و سراسری است) **لمس نمی‌شود**.

### بایدها
1. **ایزوله‌سازی:** همه رکوردها با `userId` جلسه‌ی جاری ساخته می‌شوند.
2. **اتمیک بودن:** ساخت کیف‌پول + حساب معین + سند افتتاحیه (و در صورت نیاز لات FIFO) داخل یک تراکنش `db.transaction`.
3. **تراز بودن:** سند افتتاحیه با حساب «سرمایه افتتاحیه» (کد `3010`) موازنه می‌شود تا جمع کنترلی دفتر صفر بماند.
4. **کد یکتای حساب:** چون `accounts` ایندکس یکتا `(userId, code)` دارد، باید کد جدیدِ یکتا تولید شود (نه کد ثابت).
5. **Fail-closed:** مالکیت و احراز هویت در مرزِ اکشن بررسی می‌شود (الگوی `guardActionAuth` موجود).
6. **نرخ دلار از سرور (فریز):** تبدیل تومان→USD با `getLatestUsdIrtRate` سرور انجام می‌شود، نه از ورودی کاربر.

## ۳) مدل داده — بدون تغییر اسکیما (فقط نحوه‌ی استفاده)

| موجودیت | جدول | نحوه‌ی استفاده |
|---|---|---|
| ظرف/برچسب حساب | `wallets` | `name` (نام کامل، ایزوله با `userId`)، `kind`، `note` |
| حساب معین (قابل تراکنش) | `accounts` | `type="asset"`، `assetId`=ارز/دارایی، `walletId`=اتصال، `code`=یکتا، `userId` |
| موجودی اولیه | `journalEntries` + `postings` | سند `type="opening"` از مسیر `postEntry` |
| (فقط دارایی قیمت‌دار) | `lots` | پارامتر `openLots` در `postEntry` برای رمزارز/طلا |

**نکته‌ی مهم درباره‌ی «نام بانک»:** پیشنهاد اصلاح‌شده این است که «نام بانک» به‌عنوان نام حساب در `wallets.name` ذخیره شود. این نام **ایزوله** است چون `wallets.userId` دارد. (ترجمه‌ی دقیق خواسته‌ی شما: «نام بانک را سراسری/مشترک ذخیره نکن» — نه «اصلاً ذخیره نکن»؛ چون ذخیره‌نشدنِ کلی، خودِ قابلیت را بی‌معنا می‌کند.)

## ۴) سرویس جدید (سمت سرور) — `src/features/accounts/service.ts` (فایل جدید)

### ۴.۱ ورودی (Input)

```ts
export type RegisterMoneyAccountInput = {
  name: string;            // نام کامل (مثلاً «بانک ملت — حساب جاری»)
  kind: "bank" | "cash" | "exchange" | "hot" | "cold" | "fund";
  assetId: string;         // ارز/دارایی پایه‌ی حساب (از لیست دارایی‌های معتبر)
  openingValueIrt?: string;  // موجودی اولیه به تومان (برای حساب پول/فیت)
  openingQty?: string;       // مقدار دارایی (برای رمزارز/طلا)
  openingUnitPriceUsd?: string; // قیمت واحد به دلار (برای رمزارز/طلا)
  openingDate?: string;      // تاریخ افتتاحیه (پیش‌فرض: امروز)
  note?: string;
  userId?: string;           // از جلسه، نه از ورودی کاربر
};
```

### ۴.۲ الگوریتم (گام‌ها، داخل `db.transaction`)

1. **اعتبارسنجی** با zod (نام ≥۲ کاراکتر، kind معتبر، assetId معتبر، موجودی > صفر در صورت ورود).
2. **حل assetId** (فقط از فهرست دارایی‌های فعال سیستم؛ نه ورودی آزاد).
3. **تولید کد یکتای `code`** برای حساب جدید:
   - برای حساب نوع asset، در بازه‌ی 1xxx: `max(code عددیِ حساب‌های asset همان کاربر) + 10`.
   - چون یکتایی روی `(userId, code)` است، کاربران مختلف می‌توانند کد یکسان داشته باشند (تأییدشده در `tests/multi-user-isolation.test.ts`).
4. **ساخت کیف‌پول** در `wallets` با `userId`، `name`، `kind`، `note`. (`institutionId` و `networkId` را NULL می‌گذاریم — لمس جدول مشترک `institutions` لازم نیست.)
5. **ساخت حساب معین** در `accounts`:
   ```
   { code, name, type: "asset", assetId, walletId, userId, isActive: true }
   ```
6. **ساخت سند افتتاحیه** از مسیر `postEntry`:
   - پستینگ ۱ (بدهکار): حساب جدید، `quantity/baseValue` مثبت.
   - پستینگ ۲ (بستانکار): حساب «سرمایه افتتاحیه» (کد 3010 همان کاربر یا سیستم)، منفی.
   - نوع: `opening`، `source: "manual"`.
   - **محاسبه‌ی مبلغ پایه (USD):**
     - حساب فیت (IRT): `baseValue = openingValueIrt / rate` (rate از `getLatestUsdIrtRate` سرور).
     - حساب USD/USDT: `baseValue = openingValueIrt / rate` اگر به تومان وارد شده، یا مقدار مستقیم اگر به‌دلار.
     - رمزارز/طلا: `baseValue = openingQty × openingUnitPriceUsd` + `openLots` برای ساخت لات FIFO (الگوی دقیق `setup/service.ts`).
   - اگر `openingDate` داده شده، `entryDate` همان؛ وگرنه امروز.
7. **رکورد audit** با `recordAuditEvent` (رفع شکاف قبلی که `createWalletAction` audit نداشت).
8. `revalidatePath` برای `/accounts`, `/transactions`, `/new`, `/net-worth`, `/portfolio`, `/ledger`.

**تضمین تراز بودن:** چون `postEntry` خودش `assertBalanced` را اجرا می‌کند، اگر جمع پستینگ‌ها صفر نباشد، کل تراکنش rollback می‌شود — هیچ داده‌ای نیمه‌کاره نمی‌ماند.

## ۸) رفع سه شکاف موجود (به‌عنوان بخشی از همین کار، نه تغییر هسته)

این‌ها در AUDIT قبلی پیدا شد و باید هم‌زمان پوشش داده شوند:

1. **کوئری کیف‌پول در `accounts/page.tsx` بدون فیلتر `userId` است** (خط زیر):
   ```ts
   .from(wallets).where(sql`${wallets.deletedAt} is null`)   // ← userId ندارد
   ```
   → افزودن فیلتر `userId` (کامپوننت نمایشی است، نه هسته). این مهم است تا کیف‌پولِ همنامِ کاربر دیگر، نوع/نهادِ شما را ندهد.

2. **`createWalletAction` موجود فقط `wallets` می‌سازد و نه حساب نه audit** → یا این اکشن جدید جایگزین آن می‌شود، یا در کنارش می‌ماند (تصمیم محصولی). پیشنهاد: اکشن جدید را مرجع کنیم و فرم قدیمی را به آن متصل کنیم.

3. **نوع سند `opening` در UI تراکنش فعال نیست** → این قابلیت مسیر رسمی ثبت موجودی اولیه را باز می‌کند (بدون نیاز به فعال‌کردن `opening` در فرم تراکنش).

## ۹) تست‌های جدید (فایل جدید `tests/money-account-registration.test.ts`)

الگو از `setup-wizard.test.ts` و `multi-user-isolation.test.ts`:

1. **تراز بودن:** بعد از ثبت، `sum(base_value)` همه‌ی postings صفر بماند (یا `integrityCheckAction` سبز باشد).
2. **اتصال خودکار:** حساب جدید در `getAccountBalances` و در فهرست `new/page` (کوئری accounts) ظاهر شود.
3. **ایزوله‌سازی نام و موجودی:** کاربر A حساب بانکی می‌سازد؛ کاربر B آن را در `getAccountBalances`، `getLedger`، و `getHoldings` نبیند.
4. **نام بانک در جدول مشترک نرود:** بعد از ثبت، `institutions` هیچ ردیف جدیدی نداشته باشد و نام فقط در `wallets.name` باشد.
5. **یکتایی کد:** دو کاربر کد 1xxx یکسان داشته باشند بدون خطا؛ درون یک کاربر، کد تکراری با خطای unique مواجه شود.

7. **Fail-closed:** فراخوانی بدون جلسه (در حالت چندکاربره) DENY شود.
8. **Idempotency (اختیاری):** ارسال تکراری، سند تکراری نسازد.

## ۱۱) ریسک‌ها و موارد احتیاط

- **نرخ تبدیل تومان→USD:** باید حتماً از سرور و فریز شود (همان الگوی `createTransactionAction`) تا موجودی اولیه‌ی تاریخی دست‌کاری‌پذیر نباشد.
- **کد یکتای حساب:** اگر کد ثابت بدهیم، کاربر دوم خطای unique می‌گیرد؛ باید تولید داینامیک باشد (بند ۴.۲ گام ۳).
- **مهاجرت داده‌ی قدیمی:** حساب جدید باید از ابتدا `userId` داشته باشد تا وارد چرخه‌ی `migrateLegacyFinancialData` (داده‌ی NULL) نشود.
- **تغییر ناخواسته‌ی هسته ممنوع:** هیچ تابعی در `src/features/ledger/*`، `src/domain/*`، `src/db/schema.ts` ویرایش نمی‌شود؛ فقط فایل‌های جدید اضافه و یک کوئری نمایشی در `accounts/page.tsx` فیلتر `userId` می‌گیرد.
