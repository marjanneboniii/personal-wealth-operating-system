# توازن — سیستم‌عامل ثروت شخصی

سیستم‌عامل خصوصی مدیریت ثروت شخصی و خانوادگی. خودمیزبان، بدون تله‌متری، مبتنی بر **حسابداری دوطرفه** و **دفترکل تغییرناپذیر**. هویت بصری: نیلی `#0F2440` و طلایی `#C9962D`، فونت Vazirmatn.

سند طراحی کامل (فاز ۱ تا ۹): [`docs/DESIGN.md`](docs/DESIGN.md) · سند بازطراحی تجربه کاربری — سیستم طراحی «Calm Ledger»: [`docs/UI_REDESIGN.md`](docs/UI_REDESIGN.md)

## نقشه راه‌رسم (IA)
هر مقصد یک سؤال مالی را جواب می‌دهد؛ دو لایه «مالی انسانی» و «حقیقت حسابداری» به‌روشنی جدا هستند:
* **ثروت** ▸ نمای کلی (`/`) — «وضعیت مالی من چگونه است؟»
* **پول** ▸ تراکنش‌ها (`/transactions`) · حساب‌ها · جریان نقدی · دفترکل
* **دارایی‌ها** ▸ سبد دارایی · رمزارزها · ارزش خالص (`/net-worth` با بازه‌های 1M…ALL و Change Attribution)
* **برنامه‌ریزی** ▸ پیش‌بینی · بودجه‌ها · اهداف و صندوق‌ها · بدهی‌ها · اقساط
* **گزارش‌ها** ▸ گزارش‌های مالی · حسابرسی (`/audit` — ۷ آزمون زنده یکپارچگی)

دسکتاپ: سایدبار گروه‌بندی‌شده و جمع‌شونده + مرکز فرمان `⌘K`. موبایل: Bottom Navigation با ۵ شکاف (خانه، دارایی‌ها، تراکنش‌ها، برنامه‌ریزی، بیشتر). فرم‌ها و فیلترها state را در URL نگه می‌دارند؛ دکمه back مرورگر همیشه درست کار می‌کند.

### دارایی واقعی ← ملک (Real Estate)
در صفحه «دارایی واقعی و کالا» (`/asset-registry`) بخش اختصاصی املاک قرار دارد:

* **Master Data:** شهر (پایه: اهواز)، ۱۶ منطقه/محله اهواز و ۱۲ نوع ملک در جدول‌های مرجع (`cities`، `neighborhoods`، `property_types`) نگهداری می‌شوند؛ ادمین می‌تواند آن‌ها را اضافه/اصلاح/غیرفعال کند (بدون تغییر Schema) و کاربر عادی فقط از گزینه‌های فعال انتخاب می‌کند — هیچ ورود متن آزاد برای نام، شناسه، شهر، محله یا نوع ملک وجود ندارد.
* **نام و شناسه خودکار:** نام به شکل «آپارتمان — اهواز — کیانپارس شرقی» (+ شماره ترتیبی برای ملک‌های مشابه در یک محله) تولید می‌شود. شناسه همه دارایی‌های واقعی یک دنباله عددی کوتاه و مشترک است: در پایگاه داده `001` و در رابط فارسی `۰۰۱`. شناسه یکتا و تغییرناپذیر است (Unique Constraint روی `assets.symbol`)؛ مشخصات شهر/محله/نوع در فیلدهای ساخت‌یافته باقی می‌مانند.
* **تاریخ شمسی → میلادی:** کاربر تاریخ تملک و ارزش‌گذاری را فقط به شمسی وارد می‌کند؛ سیستم معادل میلادی (ISO) را محاسبه و به‌عنوان مقدار استاندارد ذخیره می‌کند و نسخه شمسی برای نمایش/Audit کنار آن نگه‌داشته می‌شود.
* **نرخ دلار تاریخی:** قیمت خرید دلار = تومان ÷ نرخ دلارِ «تاریخ تملک» و ارزش فعلی دلار = تومان ÷ نرخ دلارِ «تاریخ ارزش‌گذاری». نرخ + منبع + تاریخ نرخ کنار هر مبلغ فریز می‌شود و هرگز با نرخ امروز بازمحاسبه نمی‌شود.
* **حسابداری دوبل:** ثبت ملک یک سند «افتتاحیه» با **تاریخِ تملکِ واقعی** ایجاد می‌کند: بدهکار حساب املاک (۱۶۰۰) / بستانکار سرمایه افتتاحیه تملک‌های تاریخی (۳۰۱۵). خریدِ پیش از راه‌اندازی سیستم به‌عنوان تملک تاریخی (Opening Balance) وارد می‌شود و **هیچ جریان نقدی در تاریخ ثبت سیستم** ایجاد نمی‌کند. تراکنش تاریخی تغییرناپذیر است؛ تغییر ارزش فعلی فقط با «ارزش‌گذاری جدید» انجام می‌شود.
* **مجموع ثروت:** ارزش فعلی (تومان و دلار با نرخِ تاریخ ارزش‌گذاری) به‌صورت خودکار در مجموع دارایی‌های واقعی، سبد دارایی و ارزش خالص (`/net-worth`) لحاظ می‌شود.
* از کارت هر ملک می‌توان به سند دفترکل (لینک `?entry=`) و بالعکس از دفترکل به ملک رفت.

### دسته‌بندی هزینه‌ها (Expense Categories)
ماژول ثبت تراکنش به **سیستم دسته‌بندی سلسله‌مراتبی هزینه‌ها** مجهز است (جدول `expense_categories` با ساختار Parent-Child):
* **۱۶ دسته اصلی استاندارد** (مسکن، خودرو و حمل‌ونقل، خوراک، سلامت، بهداشت، پوشاک، تفریح، ارتباطات، خریدهای شخصی، خانوادگی، بیمه و تعهدات مالی، آموزش، شغلی، مالیات/قانونی، کمک و هدایا، متفرقه) با زیردسته‌های دقیق و کد پایدار — سند کامل: [`docs/EXPENSE_CATEGORIES.md`](docs/EXPENSE_CATEGORIES.md).
* با انتخاب نوع «هزینه»، انتخابگر دسته فعال می‌شود؛ ثبت بدون دسته ممکن نیست (سقوط سرور به «متفرقه» فقط برای سازگاری API).
* **ضد هم‌پوشانی:** هر زیردسته یک خانه اصلی دارد و افزودن زیردسته با نام تکراری زیر یک والد رد می‌شود؛ زیردسته جدید بدون تغییر اسکیما قابل افزودن است.
* **استهلاک خودرو (`TRN-DEPR`) غیرنقدی است:** هزینه در گزارش‌ها ولی بدون خروج وجه (حساب ذخیره `3200`)؛ جریان نقدی آن را حذف می‌کند.
* **بازپرداخت بدهی نوع جداگانه است** (`debt_repayment`) و هرگز «هزینه» محسوب نمی‌شود؛ انتقال بین حساب‌ها نیز همین‌طور.
* گزارش‌ها: تفکیک درختی هزینه‌ها در `/cash-flow`، فیلتر و برچسب دسته در `/transactions`، و کادر بررسی تراکنش‌های «متفرقه».

### مسیرهای ثبت دستی و احراز هویت
* **بدهی دستی:** از بخش برنامه‌ریزی به `/debts` بروید و «ثبت بدهی دستی» را بزنید. فرم ابتدا پیش‌نمایش می‌دهد و فقط با «تأیید نهایی» بدهی/اقساط را در لایه برنامه‌ریزی ذخیره می‌کند؛ این کار هیچ `Journal Entry` یا `Posting` جدیدی نمی‌سازد.
* **نرخ ارز دستی:** در `/market-data` بخش «ثبت دستی نرخ ارز» (و همچنین `/settings`) قرار دارد. نرخ برای ارزش‌گذاری جاری است و تاریخچه، FIFO و دفترکل را تغییر نمی‌دهد؛ برای نرخ شخصی باید وارد حساب شوید.
* **ورود کاربر و Google:** لینک «ورود / ثبت‌نام» در نوار اصلی و مسیرهای `/login` و `/register` همیشه قابل مشاهده‌اند. برای فعال شدن دکمه واقعی Google Identity Services، متغیرهای `GOOGLE_CLIENT_ID` و `NEXT_PUBLIC_GOOGLE_CLIENT_ID` را طبق `.env.example` تنظیم کنید.

## فناوری‌ها
Next.js 16 (App Router, Server Components) · TypeScript · PostgreSQL · Drizzle ORM · Tailwind CSS v4 · zod · نمودارهای SVG بدون وابستگی · PWA (manifest + آیکون) · فونت Vazirmatn، RTL کامل.

## معماری
```
src/domain        هسته مالی خالص: Decimal (BigInt/18)، قواعد تراز، موتور FIFO
src/features      Use-Caseها: ledger (نوشتن/کوئری)، planning (اهداف، اقساط، پیش‌بینی)
src/db            اسکیما (۳۰ جدول)، اتصال، seed
src/app           صفحات، Server Actions، API (health/backup/restore)
src/components    Design System، نمودارها، فرم‌ها، پوسته موبایل‌اول
```
قانون وابستگی یک‌طرفه است: `app → features → domain`؛ دامنه هیچ وابستگی به Next یا Drizzle ندارد.

## اصول مالی پیاده‌سازی‌شده
* هر سند حداقل دو ردیف دارد و `Σ base_value = 0` (در `assertBalanced`).
* **هیچ ستون موجودی وجود ندارد**؛ همه مانده‌ها با `SUM(postings)` محاسبه می‌شوند.
* اصلاح فقط با **سند معکوس**؛ سند اصلی به `void` می‌رود و حذف نمی‌شود.
* خرید → باز شدن **Lot**؛ فروش → مصرف Lotها به روش **FIFO** و ثبت **سود تحقق‌یافته** در حساب `4100`.
* سود تحقق‌نیافته فقط گزارشی است و هرگز در دفترکل ثبت نمی‌شود.
* **برنامه‌های آینده** (planned_transactions، رویدادها، اهداف، تعهدات) تا لحظه «اجرا» هیچ اثری روی دفترکل ندارند؛ اجرا Idempotent است.
* پرداخت قسط یک سند دوطرفه می‌سازد و مانده بدهی را از دفترکل کم می‌کند.
* **هزینه ≠ بازپرداخت بدهی ≠ انتقال:** بازپرداخت اصل بدهی (`debt_repayment`) و انتقال بین حساب‌های شخصی هرگز به‌صورت خودکار «هزینه» محسوب نمی‌شوند.
* دسته هزینه فقط **بُعد گزارش‌دهی** سند است (`journal_entries.category_id`) و هرگز در تراز دوطرفه دخالت نمی‌کند.

## اجرا
```bash
cp .env.example .env        # DATABASE_URL=postgresql://user:pass@host:5432/db
npm install
npm run db:migrate          # ایجاد/به‌روزرسانی اسکیما (مرحله‌ای صریح، خارج از Runtime)
npm run build && npm start  # اجرای تولیدی
```

برای توسعه محلی بدون PostgreSQL، `DATABASE_URL=memory://` بگذارید؛ در این حالت اسکیما و داده نمونه به‌صورت خودکار در حافظه ساخته می‌شود (در Production این مسیر Fail-Closed است و مجاز نیست). داده نمونه فقط در حالت توسعه (`APP_MODE=development`) به‌صورت خودکار seed می‌شود؛ در Production به‌هیچ‌وجه seed خودکار انجام نمی‌شود.

اگر هنگام اجرا با خطای دیتابیس مواجه شدید (مثل `Failed query: ...`)، علت واقعی را با این دستور پیدا کنید:
```bash
npm run db:check   # سالم بودن DATABASE_URL، DNS، اتصال و اسکیما را بررسی و راهنمایی می‌کند
```

## پشتیبان‌گیری و بازیابی
* `GET /api/backup` → خروجی JSON نسخه‌دار از تمام جداول (قابل دانلود از صفحه تنظیمات).
* `POST /api/restore` → بازیابی **تراکنشی** (all-or-nothing) با بررسی نسخه اسکیما.
* توصیه عملیاتی: `pg_dump` شبانه + قاعده ۳-۲-۱ + آزمون بازیابی ماهانه.

## آزمون و صحت‌سنجی
* دکمه «بررسی یکپارچگی» در دفترکل و تنظیمات، تراز همه اسناد را با یک کوئری تجمیعی بررسی می‌کند.
* بررسی سریع در پایگاه داده:
```sql
select je.id, sum(p.base_value) from journal_entries je
join postings p on p.entry_id = je.id
group by je.id having abs(sum(p.base_value)) > 1e-9;   -- باید صفر سطر برگرداند
```

## عملکرد
تجمیع‌ها در سمت PostgreSQL انجام می‌شود؛ ایندکس روی `postings(account_id, entry_id)`، `prices(asset_id, as_of desc)`، `installments(due_date,status)` و `planned_transactions(planned_date,status)`. صفحات Server Component هستند و فقط فرم‌ها و نمودارها به کلاینت می‌روند.

## امنیت و حریم خصوصی
هیچ درخواست خارجی اجباری وجود ندارد، قیمت‌ها دستی/محلی ثبت می‌شوند، همه ورودی‌ها با zod در سرور اعتبارسنجی می‌شوند و هر نوشتن در `audit_log` ثبت می‌گردد. برای استقرار خانگی، اجرا پشت VPN/شبکه خصوصی توصیه می‌شود.
